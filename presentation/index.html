The Happy Path: Avoiding Repeated Work

Cache bypasses the slow database disk/network hop. But cheaper per request doesn't mean free.

Without Cache (3 Repeat Queries)
Req #1: Fetching DB
Req #1 Client → App → Database (Disk I/O) 500ms
Req #2 Client → App → Database (Repeat query) 500ms
Req #3 Client → App → Database (Repeat query) 500ms
Total Latency: 1,500ms
With Cache (1 Miss, 2 Hits)
Req #1: Cache MISS
Req #1 Cache Miss → Fetch DB → Store in RAM 500ms
Req #2 Cache Hit → Returned directly from RAM <1ms
Req #3 Cache Hit → Returned directly from RAM <1ms
Total Latency: ~500ms (3x faster)

What NOT to Cache: Anti-Patterns

AI defaults to caching whatever was slow. Stale reads can become severe security & inventory bugs.

1. Security: Cached Permissions

TTL: 1 hour. Admin revokes employee "write" access in DB at 10:05.

10:00: Cached ["read", "write"]
10:05: DB revokes access ["read"]
10:50: Cache returns ["write"] → Breach!
Rule: Don't cache security-critical data without explicit push invalidation.
2. Consistency: Real-Time Stock

Product has 1 item left. Cached with 10s TTL.

Alice buys item 1 → Stock becomes 0
Bob checks → Cache still returns 1 in stock
Bob checkout succeeds → Oversold (-1)
Rule: Never cache data that changes frequently and carries business liability when stale.
3. Waste: One-Time Reads

Caching last_login_at or password reset tokens in RAM.

Stored for 1 Hour: user:123:token
Read Count = 1 (never read again)
Result: Memory pollution & evicts hot keys
Rule: Cache only data expected to be read multiple times.

Scene 2: What NOT to Cache:

"AI loves to wrap functions with `@cached`. But caching permissions means revoked users still hold access for 59 minutes."

"Caching inventory count when there is 1 item left means overselling to negative inventory."

Ask the audience: Does this data change? Does stale data create legal or security liability? If yes, don't blindly cache.

Scaling Out: Local RAM vs. Shared Redis

When you add a second server, local memory creates stale drift. Shared Redis fixes drift at the cost of a network hop.

In-Memory Map: Stale Alice Bug
// Step 1: Read via Server A
Server A caches: "Alice"
// Step 2: Update Name via Server B
Server B updates DB → "Alicia"
Server B invalidates its own map
// Step 3: Read via Server A again
Server A returns cached: "Alice" ❌ STALE!
Server B cannot purge Server A's process RAM heap.
Shared Redis: Consistent Fresh Reads
// Step 1: Read via Server A
Loads DB → stores in Redis: "Alice"
// Step 2: Update Name via Server B
Server B updates DB → "Alicia"
Server B deletes key in Redis
// Step 3: Read via Server A again
Server A misses Redis → reloads "Alicia" ✓ FRESH!
Trade-off: Network hop (~1ms vs 0ms) + new infrastructure dependency.

Algorithm Mechanics: Fixed Window vs Token Bucket

Fixed Window allows a 2x burst across window boundaries. Token Bucket enforces a smooth average while allowing bursts.

Fixed Window: Boundary Burst (2x Traffic)
Timeline: 0.0s (Window 1)
t = 0.9s (End of Window 1)
5 Allowed
t = 1.1s (Start of Window 2)
5 Allowed
10 requests allowed in 0.2s! Double the stated 5/sec limit across the window reset boundary.
Token Bucket: Bursts with Constant Refill
Tokens: 5 / 5 (Full Capacity)
• Config: 5 tokens capacity, refills 1 token / sec
• Natural human bursts consume tokens instantly
• Overflow is dropped immediately without boundary doubling
Real users are bursty. Token bucket accommodates natural burstiness without doubling the boundary quota.

Scene 2 & 3: Fixed Window vs Token Bucket:

"Fixed window is simple to code with Redis INCR. But watch the boundary: 5 requests at 0.9s, reset at 1.0s, 5 requests at 1.1s."

"That's 10 requests hitting your database in 200 milliseconds!"

Token bucket provides smooth refills and models human usage much better.

Equal Distribution: Round-Robin Mechanics

Opening the Load Balancer box: cyclic routing across identical instances. Equal requests ≠ equal work.

Load Balancer Node: Cyclic Round-Robin Loop
Routing: Req #1 → Node A
// Cyclic Sequence: A → B → C (Looped 12 requests)
1:A 2:B 3:C 4:A 5:B 6:C 7:A 8:B 9:C 10:A 11:B 12:C
The Blindspot

Round-robin assumes every request costs the same and every backend performs identically.

Req #1: 1ms static JSON query
Req #2: 12,000ms PDF export task
Key Takeaway: Round-robin counts requests, not CPU cycles or queue depth.

Capacity-Aware: Weighted Distribution

Unequal servers need proportional scheduling (A:3, B:2, C:1). But routing traffic is NOT moving state.

Weighted Load Balancer: [3, 2, 1] Capacity Ratio
Schedule: [A, A, A, B, B, C]
// Weighted Sequence: [A, A, A, B, B, C] × 2 (Looped 12 requests)
1:A 2:A 3:A 4:B 5:B 6:C 7:A 8:A 9:A 10:B 11:B 12:C
Critical Callback: Routing ≠ State

“We changed where requests land, not where state lives.”

Per-server caches remain isolated in RAM
Per-server rate counters still multiply total quota
A load balancer spreads traffic. It does not synchronize memory.

Circuit Breaker: State Machine & Analogy

In software, "Open" means the circuit is broken and traffic is blocked. Open is a protective choice, not the fault.

The Three States
State Electrical Software Meaning
● CLOSED Circuit connected Calls flow normally to partner
● OPEN Circuit broken Fail fast immediately; 0 wait
● HALF-OPEN Testing loop Send 1 probe test call to check health
Key Insight: OPEN is our system actively protecting itself from slow hangs.
State Transition Cycle
STATE: CLOSED (Normal)

Episode 4 Opening:

"Every engineer gets confused by Closed vs Open. In English, 'the store is open' is good. In electronics, an OPEN circuit has no current!"

"Closed = calls flow. Open = we stopped calling. Half-open = testing if it's safe."

Explain that timeout bounds ONE call. A breaker remembers that the last 3 calls timed out and stops wasting time.

The Wrong Boundary: 1 Shared Breaker Kills All Couriers

Checkout queries 3 independent couriers (A, B, C). One global breaker disables the entire checkout when Courier B fails.

Coarse Boundary: 1 Breaker Wrapped Around All 3
[Shared Checkout Breaker: OPEN] BLOCKED
Courier A
Healthy ✓

Down ✗
Courier C
Healthy ✓

Specification Trap

“The code executed exactly as specified. The specification was the bug.”

AI will happily wrap your checkout with a circuit breaker if you ask it to "add resilience". But wrapping the wrong boundary turns a minor dependency glitch into a total site outage.
One partner failing should remove one shipping option, not shut down checkout.

Isolated Boundaries: Graceful Degradation & Recovery

Isolate breakers per dependency. Probe test calls verify recovery before restoring full traffic.

Fine-Grained Boundary: Breaker Per Courier
Courier A
[CLOSED]
Quotes: $15.00 ✓
Courier B
[OPEN]
Fast-fail (0ms) ✗
Courier C
[CLOSED]
Quotes: $18.50 ✓
Checkout #4 Customer Experience: “Quotes available from Courier A ($15) and Courier C ($18.50). Courier B is temporarily unavailable.” Sale completes!
Recovery Is Tested, Not Assumed
1. Cooldown passes → B enters HALF-OPEN
2. Single test probe admitted to B
3. Probe succeeds → B transitions to CLOSED
4. All 3 couriers available again
Traffic is restored only after evidence of recovery, never just timer assumptions.

Architecture Principles: Human Judgment in the Age of AI

AI writes code faster than you ever could. Your role is deciding the system boundaries and trade-offs.

1. Start Local, Pay Later

Don't add Redis, Kafka, or microservices on day one. An in-memory map or local token bucket is fast, simple, and has zero network failure modes.

Rule: Evolve to distributed state only when multiple instances demand consistency.
2. Routing ≠ Shared State

Adding a load balancer only balances incoming requests. It does not synchronize cache memory or unify rate limit quotas across servers.

Rule: Scaling horizontally forces you to choose between eventual consistency and shared storage latency.
3. Choose the Right Boundary

Resilience patterns are only as smart as their boundaries. Isolate circuits per dependency and choose rate-limit keys by client identity, not raw IP.

Rule: A failure in one external partner should degrade a feature, not crash the checkout.
